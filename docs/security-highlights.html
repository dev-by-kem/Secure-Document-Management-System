02 Four deep dives (if the professor asks “how?”)

A · Identity and queries

app/lib/auth.php · app/lib/db.php
  • Passwords are hashed with a per-password salt; verification happens with password_verify().
  • Every query with user input is a prepared statement with a bound parameter. Nothing is concatenated.
  • Login throttling: five failed attempts per username in fifteen minutes.
“Even the developer cannot read your password back — only reset it.”

B · Authorization policy

app/lib/rbac.php · guard on every page
  • Page guard: require_role(['admin']) on all admin pages; upload is admin + staff.
  • Object guard: can_access_document() and can_download_document().
  • Pending: owner and admin. Approved: everyone authorized. Rejected: owner may view, only admin may download. Deleted: admin only.
“A viewer cannot reach an admin URL, and a staff member cannot approve their own upload.”

C · Sessions and form defenses

app/bootstrap.php · csrf.php · validate.php · helpers.php
  • session_regenerate_id(true) after login defeats session fixation.
  • Cookies are HttpOnly and SameSite=Lax; Secure is config-driven for HTTPS staging.
  • Every form posts a CSRF token; uploads check extension and real MIME type, never the browser's claim.
  • e() escapes every dynamic value with ENT_QUOTES, UTF-8.
“The browser is never trusted — the server checks everything again.”

D · The file vault

public/documents/upload.php · download.php
  • Files are saved with a random server-generated name in storage/uploads/, outside the web root.
  • Download order: session → role → document status → SHA-256 re-check → stream → audit log.
  • Metadata insert and file move share a transaction; failures roll back and delete orphan files.
“A file can only leave this server through one checked door.”

03 Defense in depth (small things that still count)

  • Login throttling — five failed attempts per username within 15 minutes; a LOGIN_THROTTLED event is recorded.
  • Web-access guard — the root .htaccess returns 404 for app/, database/, docs/, logs/, storage/, tests/, and denies direct download of .sql, .md, .log, .json, .ps1.
  • Upload vault guard — storage/uploads/.htaccess says Require all denied as a second layer.
  • Quiet errors — display_errors=Off; details go to logs/app-*.log, users see one generic message.
  • Safe delivery headers — X-Content-Type-Options: nosniff and a sanitized download filename.
  • Secrets hygiene — config.php is gitignored, FTP credentials live in GitHub Secrets, HTTPS and session_secure_cookie=true are used on staging, and seeded passwords must be changed there.
  • Admin self-protection — an admin cannot change their own role, deactivate their own account, or deactivate the last active administrator.
  • No self-registration — all accounts are provisioned by an administrator.

05 Q&A cards — short answers, backed by code

Why bcrypt and not MD5 or SHA1?
MD5 and SHA1 are fast, so they are brute-forceable. PASSWORD_DEFAULT uses bcrypt/Argon2 with a per-password salt and a tunable cost.
How exactly is SQL injection stopped?
One hundred percent PDO prepared statements. User input is always a bound parameter, never concatenated. Show ST-01.
What if someone steals a session cookie?
HttpOnly blocks JavaScript access; regeneration defeats fixation; 30 minutes of idle time limits the window; SameSite=Lax limits cross-site replay; HTTPS protects the cookie on staging.
How is file confidentiality enforced?
Files live outside the web root. The only route is download.php, which checks session → role → status, then streams and logs.
How do you guarantee data integrity?
Foreign keys, transactions, SHA-256 checked again at download, soft delete, confirmation dialogs, and append-only audit logs.
How do you know who did what?
activity_logs plus document_access_logs — including denied attempts — with user, action, IP and timestamp.
What happens when an account is deactivated?
Login filters status='active', and identity is re-checked from the database on every request, so access ends immediately. An admin can reactivate it.
Can staff approve their own document?
No. Approval pages use require_role(['admin']), and the access policy is centralized in lib/rbac.php.
Why throttle per username, not per IP?
Our lab shares one public IP, so per-IP throttling would let one person's mistakes lock out everyone. A production system should track both and add a CAPTCHA or delay.
Is the throttling a permanent lockout?
No — it is five failures in a 15-minute window. For the demo we backdate the test rows in phpMyAdmin so the block clears instantly.

Be honest about the limits

  • No encryption at rest and no antivirus integration — listed as future work.
  • The local XAMPP demo runs over HTTP; the Secure cookie flag is enabled only in the HTTPS staging config.
  • Seeded demo passwords are public in the repository — change them on the public staging site.
  • Throttling is per username and temporary, not a permanent account lockout.
  • The .htaccess protections rely on Apache, which both XAMPP and the staging host provide.
